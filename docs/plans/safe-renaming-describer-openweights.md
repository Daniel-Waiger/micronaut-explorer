## Objective

Three user-selected clusters, decisions already made and NOT open for re-litigation:

1. **Safe-renaming hardening** — all-or-nothing batch apply with guaranteed rollback;
   preserve the original filename (sidecar always + opt-in embed); warn on locked /
   cloud-synced files; Windows path & collision edges; date-provenance honesty.
2. **Free-text describer** — plain-language experiment description → structured naming
   fields, flagged **provisional** and requiring review before apply.
3. **Open-weights model support** — auto-detect installed Ollama models, rank against a
   modern preference list, VRAM-aware, user-overridable.

Plus: extend the marker/fluorophore dictionary broadly.

**Explicitly OUT of scope:** CZI/ND2 key maps and any test requiring a real vendor
fixture (no sample files exist yet — `tests/data/` is empty by design). Web re-platform
and the experimental-design assistant stay parked.

## Ground truth — established by the orchestrator, DO NOT re-derive

Per lesson 32, these were verified live against the working tree during planning.
Treat them as fact and spend your budget on implementation, not investigation.

- `apply_batch` (service.py:235) renames in a bare loop and calls `save_manifest`
  **after** the loop. A failure at file 3 of 10 leaves files 1–2 renamed with **no
  manifest written at all** → unrollbackable. This is a live defect, confirmed by
  reading the code, not a hypothesis.
- `save_manifest` returns `None` when `planned` is empty or every `src == dst`, and
  uses `src.relative_to(input_dir)` (raises `ValueError` for a path outside `input_dir`).
- `rollback_manifest` already unwinds in reverse order and skips entries whose original
  already exists. Reuse its semantics; do not duplicate them.
- `apply_batch` call sites are exactly three: `cli.py:203`, `cli.py:248`,
  `app_streamlit.py:526`. All three currently let exceptions propagate.
- `resolve_ollama_model` and `list_local_ollama_models` already exist in llm.py.
  `DEFAULT_PREFERRED_MODELS` is stale: `["llama3.1:8b", "qwen2.5-coder:7b", "phi3:mini"]`.
- `suggest_fields_with_ollama` already accepts `user_description`; `suggest_for_file`
  and `plan_batch` already thread `user_description` through. The describer's plumbing
  exists — C1 is about structure + provisional tagging, not new wiring.
- `markers.py` has 27 canonical entries.
- Target hardware: 64 GB RAM / 16 GB VRAM (a 14B model fits fully on GPU).
- Baseline: `pytest -q -m "not integration"` = **95 passed**; `pytest -q -m integration`

## Task detail

### A4 — Windows path & collision edges

**Scope.** EDIT `naming.py`, `validation.py`, and the conflict block in `service.py`
(~lines 118–145, `conflict_strategy` handling), plus tests.
(1) **Reserved names**: reject/repair Windows device names (`CON`, `PRN`, `AUX`, `NUL`,
`COM1`–`COM9`, `LPT1`–`LPT9`) as the filename stem, case-insensitively and also when
followed by an extension (`CON.tif` is reserved).
(2) **Case-insensitive collisions**: the existing `suffix` strategy compares target names
case-sensitively; on Windows `A.tif` and `a.tif` are the SAME file, so a plan can contain
two entries that silently overwrite. Compare planned targets case-insensitively (casefold).
(3) **MAX_PATH**: warn (do not silently truncate) when a full target path would exceed 260
characters; surface as a `ValidationIssue`, since truncation destroys identity.
(4) **Unique suffix**: replace the bare `_NN` collision suffix with a
distinguishable component (short timestamp or content-derived token) so two genuinely
different acquisitions never become indistinguishable. Keep `_NN` behaviour reachable if a
config/flag already selects it; do not break the existing `skip`/`fail` strategies.
INVARIANT: `BatchResult.planned` stays 1:1 with filesystem entries; never emit two entries
for one source. Do not change `apply_batch` (that is A1).

**Verification.** Fast suite green (>= 95). New tests must prove, by execution not
inspection: `CON.tif` is caught; a plan containing `A.tif` and `a.tif` does not produce two
targets that collide case-insensitively; a >260-char path yields an issue rather than a
truncated name; two colliding sources get distinguishable (not `_01`/`_02`-ambiguous)
targets. ruff + black clean.

Keep `canonical_markers()` / `alias_map()` signatures unchanged.

**Verification.** Fast suite green (>= 95). Tests must include explicit false-positive

### A1 — Transactional apply + guaranteed rollback

**Scope.** EDIT `service.py` (`apply_batch`) and `manifest.py` (+ tests).
Deliver **all-or-nothing** semantics (the user's explicit choice):
(1) Write the manifest as an **intent journal BEFORE** any rename, so a hard crash
(power loss, kill -9) still leaves a recoverable trail — the current
rename-then-manifest order cannot survive that.
(2) Rename each planned pair. On ANY exception, **undo every rename already completed**,
in reverse order, then re-raise the ORIGINAL exception (chained with `raise ... from`).
Re-raising rather than returning keeps all three call sites (`cli.py:203`, `cli.py:248`,
`app_streamlit.py:526`) working unchanged — they already propagate — while guaranteeing
the filesystem is left clean. **Do not change the `tuple[int, Path | None]` return arity.**
(3) If the undo itself fails, do NOT swallow it: surface which files could not be restored
in the raised error's message, since that is the one state a user must act on manually.
(4) Reuse `rollback_manifest`'s existing reverse-order/skip-if-original-exists semantics
rather than reimplementing them.
INVARIANT: `save_manifest` returns `None` for an empty or all-`src == dst` list — the new
code must handle a `None` manifest path without crashing. Do not touch `plan_batch`,
`recalculate_batch`, or `build_series_rows`.

**Verification.** Fast suite green (>= 95). Tests must prove the MECHANISM (lesson 20),
using a monkeypatched `Path.rename` that succeeds twice then raises: assert every renamed
file is back at its original name, the original exception propagates, and a manifest
exists on disk describing the attempt. Also assert a clean batch still returns
`(count, manifest_path)` identically to today, and that an empty plan still returns
`(0, None)`. ruff + black clean.

### A2 — Original-name preservation (sidecar always + opt-in embed)

**Scope.** EDIT `manifest.py` (or a new small module) and `service.py` (+ tests).
Builds on A1 — expect an already-modified tree; do not revert A1.
(1) **Sidecar (always, every format):** maintain a durable ledger mapping current name →
original name that survives independently of the timestamped `.manifests/` files, so
identity is recoverable even if the manifest is lost or files are moved. Appending to a
single ledger per folder is preferred over one file per image. It must be **append/merge,
never replace** — a second batch in the same folder must not erase the first batch's
records (cf. lesson E6's map-replacement bug).
(2) **Embed (opt-in, narrow, default OFF):** ORCHESTRATOR-APPROVED SCOPE REDUCTION —
embedding is implemented **only for TIFF/OME-TIFF** (e.g. an ImageDescription/tag field)
and is **disabled by default**. It is NEVER applied to CZI/LIF/ND2: rewriting a proprietary
raw container contradicts the raw-data-immutability (ALCOA) posture in ROADMAP.md. If
embedding is enabled and the format is unsupported, skip silently-but-reportedly; never
corrupt or rewrite a vendor raw file.
INVARIANT: renaming must never depend on the embed step succeeding — a failed embed must
not fail or roll back the rename. The sidecar is the source of truth.

**Verification.** Fast suite green (>= 95). Tests must prove: the ledger records
original→new for a renamed file; a SECOND batch in the same folder preserves the first
batch's entries (the merge gate); embed defaults OFF; with embed enabled a non-TIFF format
is skipped without mutating the file (assert bytes unchanged); an embed failure does not
undo the rename. ruff + black clean.

### A3 — Warn on locked / cloud-synced files

**Scope.** NEW module (e.g. `safety.py`) + a surface in `service.py` (+ tests).
Builds on A1/A2 — expect an already-modified tree.
(1) Detect files that cannot be safely renamed: currently open/locked by another process
(on Windows, an exclusive-open attempt is the reliable probe), and read-only.
(2) Detect cloud-synced locations (Google Drive, OneDrive, Dropbox, iCloud) by path
heuristics — **this repo itself lives on Google Drive**, so this is a real and testable
condition, not hypothetical. A synced folder means a rename may propagate remotely or race
with the sync client.
(3) Surface findings as **warnings on the plan/preview** (e.g. via `ValidationIssue` or a
dedicated field on the suggestion/batch), never as a hard block — the user decides.
INVARIANT: detection must be **cheap and never raise** — probing must not open pixel data,
must not hang on a network path, and any probe failure degrades to "unknown, no warning".
Do not change `apply_batch` semantics from A1.

**Verification.** Fast suite green (>= 95). Tests must prove the mechanism, not the
surface: a file held open is reported (or, if the OS makes that untestable in-process, a
monkeypatched probe proves the code path); a path under a simulated Google Drive/OneDrive
root produces a sync warning while a plain temp path does not; a probe that raises produces
no warning and no exception. ruff + black clean.

### A5 — Date-provenance honesty (mtime vs acquisition)

**Scope.** EDIT `metadata.py` and `service.py` (+ tests).
Builds on earlier tasks — expect an already-modified tree.
`date` may come from real acquisition metadata, from the filename, or from **file mtime**
— and mtime is frequently the COPY date, not the acquisition date, which silently
manufactures a wrong date in the filename.
(1) Distinguish these origins in the existing `sources` provenance map rather than
collapsing them: an mtime-derived date must be distinguishable from a metadata-derived one
(the current `"filename"` tag covers both filename and mtime heuristics — split them).
(2) Make the weaker origin visible to callers so C2 can flag it.
INVARIANT E7: provenance must not pair a final (LLM-filled or edited) value with a key it
did not come from. INVARIANT (lesson 34): this touches `metadata.py` extraction routing, so
verification MUST run `pytest -q -m integration` explicitly as well as the fast suite — the
ImageJ/`_detect_format` tests are deselected by default. Do not regress
`extract_metadata_detailed`'s 3-tuple return arity or `ExtractionDetail`'s existing fields
(7 test fakes depend on both).

**Verification.** Fast suite green (>= 95) AND `pytest -q -m integration` (3 ImageJ tests
pass, 4 fixture tests skip). Tests must prove an mtime-sourced date carries a different
provenance tag than a metadata-sourced one, and that a metadata-sourced date is unaffected.
ruff + black clean.

## Risks

- **Highest — a rollback that itself fails leaves the folder in a state no manifest
  describes.** Mitigation: A1 writes the manifest as an intent journal BEFORE renaming and
  is required to surface un-restorable files explicitly rather than swallowing the error;
  its verification drives a mid-batch failure by monkeypatching `Path.rename`.
- **Embedding original names into vendor raw containers would corrupt irreplaceable
  acquisition data.** Mitigation: A2's scope hard-limits embedding to TIFF/OME-TIFF,
  defaults it OFF, and its verification asserts a non-TIFF file's bytes are unchanged.
- **Broadening the marker dictionary multiplies substring false positives** (the exact
  bug P2-1b existed to kill). Mitigation: B1 mandates word-boundary matching, longest-alias
  precedence, and explicit false-positive test gates.
- **Two tasks (C1, D1) edit llm.py and five edit service.py.** Concurrent edits would
  collide. Mitigation: batching is by file disjointness (lesson 31) — only A4/B1/D1 run in
  parallel; every service.py task is serialized, and each scope carries the dirty-tree note
  (lesson 14).
- **A5 touches metadata.py format routing, whose only coverage is `integration`-marked and
  deselected from the default run** (lesson 34 / E4). Mitigation: A5's verification names
  `pytest -q -m integration` explicitly.
- **Provisional tagging could silently degrade real provenance** if the new tag overwrites
  `"metadata"`. Mitigation: C1 forbids overwriting metadata-supplied values and requires a
  test proving it; E7 forbids pairing a final value with a key it did not come from.
